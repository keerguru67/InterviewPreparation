Q4. how will you validate if source is having 2000 records and target is having 1800 records?

1. Validate source and target counts

SELECT COUNT(*) FROM source_table;
SELECT COUNT(*) FROM target_table;

Confirm that the counts are actually 2,000 and 1,800.

2. Check the ETL mapping and business rules
I would verify whether the ETL has any filters, joins, lookups, or business rules that intentionally exclude records.
Check rejected/error records
I would check the ETL reject/error tables and session logs to see whether the 200 records were rejected because of data-quality issues, nulls, invalid formats, duplicate keys, etc.

3. Identify the exact missing records
I would compare the source and target using the business key.

For example:

SELECT s.customer_id
FROM source_table s
LEFT JOIN target_table t
  ON s.customer_id = t.customer_id
WHERE t.customer_id IS NULL;

This will help identify the source records that are missing in the target.

4. Analyze the 200 missing records
I would categorize them:
Filtered by business rule
Rejected due to invalid data
Duplicate records
Failed lookup/join
Failed transformation
Already loaded in a previous incremental run
ETL/job failure
5. Validate transformation and joins
If the mapping contains inner joins, I would check whether the 200 records are being eliminated because matching records are unavailable in lookup/reference tables.
Check batch/job logs
I would verify the ETL session/job status, rejected-record count, source file count, commit/rollback information, and any errors.
Perform source-to-target reconciliation
After identifying the reason for the difference, I would determine whether the 200-record difference is expected according to the business requirement.

note: If the requirement says all 2,000 source records must reach the target and there is no valid exclusion rule, then the missing 200 records would be treated as a defect.

5. If the interviewer asks "What if there are no filters or business rules?", say:

"Then I would identify the exact 200 missing business keys, trace those records through the ETL flow, check joins/lookups and reject tables, and determine where they were dropped. If the records are not rejected or intentionally excluded and the job completed successfully, I would raise a defect with the evidence from source, target, logs, and reconciliation results."

Q5. what is CTE function write a query using it

CTE stands for Common Table Expression. It is a temporary result set created using the WITH clause. I use CTEs to break complex queries into smaller logical steps, especially for reconciliation, duplicate identification, aggregation, and source-to-target validation. A CTE exists only for the duration of that SQL statement."

Question: Find IT employees whose salary is greater than 70,000.

WITH IT_Employees AS (
    SELECT emp_id, emp_name, salary
    FROM employee
    WHERE department = 'IT'
)
SELECT emp_id, emp_name, salary
FROM IT_Employees
WHERE salary > 70000;

Output:

102  Priya  80000
104  Divya  90000

WITH Duplicate_Customers AS (

Q6. write a query using windows functions?
"Find the highest salary employee in each department."

Example using ROW_NUMBER()
SELECT emp_id,
       emp_name,
       department,
       salary
FROM (
    SELECT emp_id,
           emp_name,
           department,
           salary,
           ROW_NUMBER() OVER (
               PARTITION BY department
               ORDER BY salary DESC
           ) AS rn
    FROM employee
) t
WHERE rn = 1;
How it works
ROW_NUMBER() OVER (
    PARTITION BY department
    ORDER BY salary DESC
)
PARTITION BY department → creates a separate group for each department.
ORDER BY salary DESC → highest salary gets number 1.
ROW_NUMBER() → assigns a sequence number to each row.
WHERE rn = 1 → returns the highest-paid employee from each department.
Another very important ETL interview example: duplicate records
SELECT *
FROM (
    SELECT customer_id,
           customer_name,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY updated_date DESC
           ) AS rn
    FROM customer
) t
WHERE rn > 1;

This identifies duplicate customer records, keeping the latest record as rn = 1.

Other window functions you should know
Function	Common use
ROW_NUMBER()	Assign unique sequence numbers
RANK()	Ranking with gaps for ties
DENSE_RANK()	Ranking without gaps
LEAD()	Compare with the next record
LAG()	Compare with the previous record
SUM() OVER()	Running/cumulative totals
COUNT() OVER()	Count records without collapsing rows

Interview tip: For an 8+ year ETL QA role, be prepared to explain ROW_NUMBER, RANK, DENSE_RANK, LAG, and LEAD with real data-validation scenarios.

Q7. lead and lag function explanation
LAG is used to access the previous row and LEAD is used to access the next row without using a self-join. In ETL testing, I can use them to compare consecutive transactions, identify changes between records, validate sequence-based transformations, and perform source-to-target data validation."

Q8. a table which will be having daily transactions I want to get the tran amount of the today's latest transaction for example I have done 4 transaction consider tran eff_dt

If your table has multiple transactions for the same day/customer, and you want the transaction amount of today's latest transaction based on tran_eff_dt, you can use ROW_NUMBER().

Assume the table is:

transactions

customer_id	tran_id	tran_eff_dt	tran_amount
101	T001	2026-09-22 09:10	500
101	T002	2026-09-22 11:30	800
101	T003	2026-09-22 14:20	1200
101	T004	2026-09-22 16:45	900

You want T004 → 900, because it is today's latest transaction.

Query using ROW_NUMBER()
SELECT customer_id,
       tran_id,
       tran_eff_dt,
       tran_amount
FROM (
    SELECT customer_id,
           tran_id,
           tran_eff_dt,
           tran_amount,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY tran_eff_dt DESC
           ) AS rn
    FROM transactions
    WHERE TRUNC(tran_eff_dt) = TRUNC(SYSDATE)
) t
WHERE rn = 1;
If you only want today's latest transaction amount
SELECT tran_amount
FROM (
    SELECT tran_amount,
           ROW_NUMBER() OVER (
               ORDER BY tran_eff_dt DESC
           ) AS rn
    FROM transactions
    WHERE TRUNC(tran_eff_dt) = TRUNC(SYSDATE)
) t
WHERE rn = 1;

Result:

900

Q10. What is fact & Dimension Table which table will be loaded first fact or Dimension table
A Dimension table contains descriptive information such as customer, product, account, and date attributes, whereas a Fact table contains measurable business events such as transactions, sales, payments, and their corresponding measures.

For example, Customer Dimension may contain customer name, city, and customer key, while Transaction Fact may contain transaction amount, transaction date, and customer key.

Generally, dimensions are loaded before facts because the Fact table contains foreign keys that reference the Dimension tables. So the typical loading sequence is staging, dimensions, and then fact tables.

As an ETL tester, I would also validate the dimension key lookups before validating the fact load, and ensure that every valid foreign key in the fact table maps to the appropriate dimension record.

Squece: Source → Staging → Dimension → Fact

Q11. how will you insert or update records without upsert
In an ETL project, records don't necessarily need to be inserted or updated manually by a user. The ETL workflow can automatically perform the operation based on business keys. For example, we can use an Insert/Update transformation in Informatica, or use a SQL MERGE statement. If the business key already exists in the target, we update the record; if it doesn't exist, we insert it.

Q12. what is a surrogate key explain?
A surrogate key is a system-generated unique identifier used in a data warehouse, mainly in dimension tables. It does not have any business meaning.

For example, the source may have customer_id = C1001, but the warehouse Customer Dimension may generate customer_sk = 101. The fact table will use customer_sk as the foreign key.

Surrogate keys are especially useful for Slowly Changing Dimension Type 2 because when a customer's attribute changes, we create a new dimension record with a new surrogate key while retaining the old record for historical reporting.

As an ETL tester, I validate that the surrogate key is uniquely generated, the correct surrogate key is assigned during dimension lookup, and the fact table receives the correct dimension key.

Q13. what is SCD type2 and how it is used in you project?4
SCD Type 2 is used to maintain the complete historical information of changes in a dimension.

In my project, we used SCD Type 2 for customer or account-related dimensions where changes such as address, customer status, or other business attributes needed to be historically tracked.

For example, if a customer was initially associated with Chennai and later moved to Bangalore, we would not overwrite the existing Chennai record. We would expire the old record by updating its end date and current flag, and then insert a new record with a new surrogate key, the new Bangalore value, a new effective date, and current flag as 'Y'.

As an ETL tester, I validate that the old record is correctly expired, the new record is inserted with a new surrogate key, effective and end dates are correct, only one record is marked as current, and the historical record remains unchanged.

SCD = Slowly Changing Dimension.

SCD Type 2 is used when we want to maintain the complete history of changes to a dimension record.

For example, suppose a customer initially lives in Chennai and later moves to Bangalore.

Instead of updating the Chennai record, SCD Type 2 expires the old record and creates a new record.

Customer SK	Customer ID	Customer Name	City	Effective Date	End Date	Current Flag
101	C1001	Ravi	Chennai	2026-01-01	2026-06-30	N
205	C1001	Ravi	Bangalore	2026-07-01	NULL	Y

Here:

Customer ID = business key
Customer SK = surrogate key
Effective Date = when this version became valid
End Date = when this version stopped being valid
Current Flag = identifies the latest record
How it works in an ETL project

Suppose today's source record is:

C1001 | Ravi | Bangalore

But the target currently contains:

C1001 | Ravi | Chennai | Current_Flag = Y

During ETL processing:

Step 1 – Identify the existing record

The ETL looks up customer_id = C1001.

Step 2 – Compare attributes

It compares the source city with the existing dimension record.

Source:  Bangalore
Target:  Chennai

Since the value has changed, it is treated as a new version.

Step 3 – Expire the old record

UPDATE customer_dim
SET end_date = CURRENT_DATE - 1,
    current_flag = 'N'
WHERE customer_id = 'C1001'
  AND current_flag = 'Y';

Step 4 – Insert the new version

INSERT INTO customer_dim
(customer_sk, customer_id, customer_name, city,
 effective_date, end_date, current_flag)
VALUES
(205, 'C1001', 'Ravi', 'Bangalore',
 CURRENT_DATE, NULL, 'Y');
